## Getting started

```powershell
# Build, launch, capture -- without ever opening the editor
& "tools/build.ps1" -Run
```

That is all: the first build **imports the project itself** (it generates `Library/` and
`ProjectSettings/` -- reckon on ~20 min), so there is nothing to open in Unity Hub beforehand.

`build.ps1` finds Unity on its own among the Unity Hub installations, then keeps its path in
`tools/local.settings.json` (not versioned). If it cannot find it -- Unity installed on another
drive, for instance -- teach it once:

```powershell
& "tools/configure.ps1" -UnityPath "<unity-folder>\__UNITY_VERSION__\Editor\Unity.exe"
```

## The three structuring choices

**1. The scene is an artefact, not a source.** `Assets/Scenes/Game.unity` is regenerated by
`SceneBuilder.Build()` at every build. You add an object to the game **by writing code**, not by
clicking in the editor. In exchange, the whole game can be driven from the command line -- build,
launch, inject keys, capture -- and therefore checked without a human hand.
WARNING: corollary -- the scene comes out modified after every build. Discard it
(`git checkout --`) unless `SceneBuilder.cs` has changed.

**2. Every numeric rule lives in `Assets/Scripts/Rules/`**, in a static class with no engine
dependency, with its tests. `dotnet test tests/__NAMESPACE__.Tests.csproj` runs in a few seconds,
without Unity -- and a hook replays them after every edit.

**3. The binary carries its identity.** Every build writes `build_stamp.json` and a
`v<version>-<sha>` stamp displayed at the bottom right. Neither a file's date (incremental build) nor
the Windows metadata (which describes the engine) says which version you are looking at. This stamp
does.

## Useful commands

| Goal | Command |
|---|---|
| Windows build | `& "tools/build.ps1"` |
| Web build | `& "tools/build.ps1" -Target web` |
| Build + launch + capture | `& "tools/build.ps1" -Run -Capture docs/x.png` |
| Tests | `dotnet test tests/__NAMESPACE__.Tests.csproj` |
| Launch and capture | `py tools/drive_game.py --launch --capture docs/x.png` |
| Serve the web build | `py tools/serve_web.py` (WARNING: **no cache** -- see PITFALLS) |
| Publish | `& "tools/release_itch.ps1" -Version X.Y.Z -DryRun` |
| Say where Unity and Python are | `& "tools/configure.ps1" -UnityPath "..."` |

WARNING: **the Unity editor must be closed** for any command-line build -- `build.ps1` refuses to
start otherwise.
WARNING: only call `Unity.exe` by hand if you know why: its path changes from one machine to the
next, and launched with `&` in PowerShell it returns **immediately without doing anything**
(`Start-Process -Wait`). `build.ps1` handles both.
